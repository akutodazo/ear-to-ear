# 決定（K1〜K17）

変えるときは理由を書いて本人の承認を取る。各項目は「背景 → 決定 → 理由」。

| # | 決定 | 理由 | 日付 |
|---|---|---|---|
| K1 | 委員は**送るだけ**。番号は仕組みが候補を出し、人が確定 | 委員の手間を LINE と同じにする（増やさない） | 10-22 |
| K2 | **未確定でも先に共有** | 一人の作業待ちで共有を止めない | 10-22 |
| K3 | **写真の前処理はブラウザ**、Worker は検査と保存だけ | Workers Free は CPU 10ms/リクエストで 12MB の写真を処理できない。撮影位置を端末の外に出さない効果もある | 10-29 |
| K4 | 番号の確定は**管理者** | 誤りの責任の所在をはっきりさせる | 10-22 |
| K5 | 書き込みだけ合言葉、閲覧は合言葉なし | 委員の手間を増やさない。個人アカウントを持たない | 10-22 |
| K6 | 撮影位置と圃場位置は別物。**撮影位置は端末の外に出さない**（座標も候補までの距離も送らない・保存しない）。送るのは候補の番号（近い順）だけ | 距離3つと既知の圃場位置から撮影位置を約0.3mで復元できる。候補の番号から「どのあたりか」が分かることは許容する | 10-22（10-31 強化） |
| K7 | 二重登録の判定は**元ファイルのハッシュ**。圃場に依存させない | 番号の訂正と衝突させない。限界: 保存し直し・LINE の再圧縮は別ファイルなので弾けない | 10-22 |
| K8 | 主張は「委員の手間を増やさずに、一人の作業を待たずに共有できる」 | 全体の省力化は測れていない | 10-22 |
| K9 | 主役は「委員会の共有と判断の記録」。画像の見比べ（L5）は補助 | 「画像解析ツール」が作成禁止の例にある。機能の重心で守る | 10-30 |
| K10 | データは**全部架空**。実在の農家の位置情報・写真・判断を、リポジトリ・開発用とデモ用の環境・動画・Claude API のどこにも入れない | 公開リポジトリ、主催者への永続の利用許諾、閲覧に認証が無い | 10-30 |
| K11 | **水分は推定しない** | 推定には2〜3年分の実測との突き合わせが要る（農試） | 10-30 |
| K12 | 既存プロジェクト（Drone Shot・field_share など）は入れない・映さない | 規約（新規制作のみ・権利のないコード不可） | 10-30 |
| K13 | GitHub・Cloudflare は既存のアカウント。資源は新規（`harvest-share-*`） | ハッカソン後も管理しやすい | 10-30 |
| K14 | 中心は「**写真を見つける**」と「**判断を根拠付きでたどれる**」。実施順 L0→L1→L6→L8→L5（実験）→L4→L9 | 父の困りごとに直接答える。L6 は判断の理由が記録されていないと時系列の言い換えにしかならない | 10-31 |
| K15 | L8 は LINE の無料枠（月200通）で運用。通知が失敗しても本体は止めない | 委員は少人数 | 10-31 |
| K16 | **水分の値は扱わない**（L2・L3 をやめる）。農協の判定は L1 の理由の選択肢（「農協の判定で中止（水分超過）」「同（砕けなどの傷）」）として残す | 水分は収穫後に農協でトラックの荷ごとに測られ、可否は無線でその場で伝わる。畑ごとの値が残らない | 11-01 |
| K17 | **L6 の根拠付けは Claude API の引用（Citations）機能**。記録1件をカスタムコンテンツの1要素として渡し、要素の番号から元の記録に戻す | 根拠は必ず渡した記録のどれかを指すと API が保証する。構造化出力とは併用できないので L6 では使わない | 11-01 |

## 期間中の決定（日付つきで追記）
- 11-02 リポジトリ名 `ear-to-ear`、最初から公開で作る。副題「穂から穂へ、写真と判断をつなぐ」とロゴをセットで出す
- 11-02 担当は層で分ける（AGENTS.md §2）。先輩は L0 のサーバーの中心だけ
- 11-02 T00: Next.js 16（App Router・`output: 'export'`）。`cacheComponents` は Node.js サーバーが要るので外した。`@types/node` は実行環境に合わせて 24 系。`check:safety` は名前の検査のみ（中身は T17）
- 11-02 GitHub の設定: Secret scanning と Push protection をオン／コミットのメールは noreply／main の Ruleset（削除禁止・force push 禁止・PR 必須・CI `check` 必須）／マージ後のブランチ自動削除／Dependabot alerts だけオン（自動の更新 PR はオフ）。GitHub Pages は使わない。Actions に Cloudflare の秘密を置かない（デプロイは本人の手元から。期間中は自動デプロイにしない）
- 11-02 **main へのマージに要る承認は 0**（最初は 1）。背景: 自分の PR は自分で承認できず、承認 1 では本人だけでマージできなかった。決定: 承認を 0 にし、PR 必須・CI 必須は残す。理由: 先輩の作業を増やさない。レビューは「書いた側と違う側」を運用で守る（AGENTS.md §3）
- 11-02 **P15 架空の圃場を置く範囲**（本人決定）。背景: 架空の圃場は実在の農地と結び付けない（K10）が、動画では畑らしく見せたい。決定: 座標は**沖合の四角**（北緯 41.800〜41.815、東経 144.500〜144.520、約 1.7km 四方の太平洋上。国土地理院の標高データが無い＝海であることを 11-02 に確認）の中に 12 圃場（A-01〜A-12、4列×3行）を機械的に並べる。画面は**地図タイルを出さず、区画と道を自分で描いた「架空の村」**にする。本番で実在の圃場に使うときは、設定で国土地理院の地図に切り替える。理由: 座標が海の上なら、地図を誤って重ねても実在の農地は出ない。安全検査で「架空データの座標がこの四角の中にあるか」を簡単に確かめられる。背景を描く手間は増える
- 11-02 **開発での Claude の使い分け**（本人決定）。背景: 期間は6日、人が確かめる時間がいちばん足りない。下のモデルや別の助手に任せると、結果を確かめる手間と読み違いが増える。決定: レビューは撮影位置・実データ・秘密に関わる PR と提出前の全体だけ、書いた会話を見ていない別の Opus のセッションで行う／詰まったとき（やり方を変えて3回か30分で決まらず、判断材料が欠けている・実用になるか判断できない）だけ新しいセッションで Fable に相談／Codex の点検とサブエージェントは基本使わない（別の会社のモデルの目が要るときだけ Codex）。理由: モデルを下げずに独立した目を持てる。審査の「目的に応じて選び、使い分けているか」にも理由つきで答えられる（AGENTS.md §3）
