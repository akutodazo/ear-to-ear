## 1. 重要な判断と根拠（D1〜D14）

形は「判断 → 根拠 → 採用しなかった案 → 影響する所」。

### D1. 方向性は案 A「台帳」。写真は証拠、鍵は番号・状態・日付
- 根拠: 中心は「写真を見つける」「判断を根拠付きでたどれる」（K14）で、どちらも文字の情報が鍵。spec §7「一覧では番号・日付・写真・判断の色だけ」。屋外の可読性（`globals.css` 冒頭）。期間内に今の CSS の延長で作れる
- 採用しなかった案: B「アルバム」（写真の上の文字が太陽光下で読めない、文字の情報の置き場が弱い）、C「地図の盤面」（委員のスマホで入口が遠い、集計のタイルはテンプレート感の源、L1 が前提）。詳細は `design-direction.md` §3
- 影響: 全画面。B の格子は圃場ページの中に、C の地図は入口として残す

### D2. 配色は 11-03 の決定をそのまま使い、足したのは「段」だけ
- 根拠: ブランド青 `#1f6fb5`・麦色 `#d9b44a`・「役割で分ける」は本人の決定（`decisions.md` 11-03）。新しい色相は足さない。足したのは 麦色の濃い段（線用、3:1 のため）、緑と灰の薄い段（判断の区画の塗り）、赤の薄い段（誤りの面）、灰（収穫済）
- 採用しなかった案: 新しいアクセント色（紫・橙など。理由が無い）、麦色を「注意」にも使う（意味が 2 つになる。Z1）
- 影響: DS §3

### D3. ライト固定。ダークモードは作らない
- 根拠: 唯一の屋外の操作（送る）は直射日光下で、白地・濃い文字が最も読める（推定だが、部品集の分析で「ダーク地＋発光」を使わない理由と同じ）。`color-scheme: light` は既存。期間が短く、2 つの配色を確かめる時間が無い
- 採用しなかった案: `prefers-color-scheme: dark` に追従（夜に新着を見る場面では楽だが、確かめる手間が倍）
- 影響: DS §2。将来足すなら用途トークンの値を差し替えるだけで済む形にしてある

### D4. 判断の色は 収穫可能＝緑、収穫済＝灰（11-04 本人決定。Q1）
- 根拠: 収穫可能は「これから動く」で注意を引く色、収穫済は「終わった」で静かな色。緑は既存 `--success` と同じ値で「できた」の意味と重なるが、両方とも肯定の意味なので衝突しない。赤は誤り・矛盾にだけ残す
- 採用しなかった案: 収穫済＝青（青は押せるもの・確定の色で意味が 3 つになる）、収穫済＝麦色（麦色は未確定だけ）、信号の 3 色（赤を「中止」に使う案。「農協の判定で中止」は理由であって判断ではない。K16）
- 影響: DS §3-2、§12-3、§12-12、§12-14。地図・圃場の見出し・履歴

### D5. 「仮のもの」は仮に見せる（麦色の線・灰の文字・破線）
- 根拠: 「未確定でも先に共有」（K2）は、未確定が確定に見えないことが前提。L6 の「根拠なし」は灰色と spec §7 に明記。「日付不明」は推測しない（型の注釈）
- 採用しなかった案: 文字だけで区別（流し読みで見落とす）、未確定を赤で（誤りではない）
- 影響: DS P4、§6-2、§12-3、§12-7、§12-14、§12-15

### D6. 影を使わず 1px の線で面を分ける。角は 4・8・16 の 3 段
- 根拠: 屋外で薄い影は見えない。beautiful-shadows 自身が「低コントラストの画面で境界線の代わりに影に頼らない」と言う。角の段は frontend-design の「全部同じ角丸にしない」。ボタンだけ 16px にして「押せるもの」を形で分ける
- 採用しなかった案: 多層の影（見えない、電池）、カードも 16px のまま（押せるものと入れ物が同じ形）
- 影響: DS §6、S5（カードの角 16 → 8）

### D7. 押せる所は 56px、本文は 18px（既存）。文字の大きさを幅で変えない
- 根拠: 手袋（`globals.css`）。WCAG の推奨 44px を上げた。屋外で小さくする理由が無い
- 採用しなかった案: PC で密度を上げるために 16px に下げる（管理者が確定する作業は PC でも 18px で困らない）
- 影響: DS §4、§7-1、§9

### D8. 動きは「送れた」の 1 か所に集中。自動の動きは無し
- 根拠: oil-ui の「記憶に残る瞬間は 1〜2 か所」、frontend-design の「動きは操作への応答だけ」。委員が畑で得たい確認は「送れた」の 1 つ。電池と電波
- 採用しなかった案: 行の入場アニメ、ローダー（Dot Matrix）、骨組み（skeleton。12 圃場・50 枚の規模で 1 秒前後と推定し、文字で足りる）
- 影響: DS P5、§8、§12-8、§12-16

### D9. 結果は押した所の近くに出す。トーストは作らない
- 根拠: 屋外で視線が画面の端に動かない。消える通知は読み直せない。既存の実装（写真ごとの結果、フォームの下の文）と同じ
- 採用しなかった案: 画面の下のトースト（Efferd の Toast は PC の管理画面向け）
- 影響: DS §7-4

### D10. 取り消しは 2 段（同じ場所のボタンが変わり、5 秒で戻る）。モーダルは作らない
- 根拠: 手袋の誤タップ。判断の取り消しは記録として残るが（spec §3 の L1）、戻しにくい。モーダルは画面の外へ指を動かし、屋外で読みにくい
- 採用しなかった案: Kokonut の「長押しで確定」（iOS のコンテキストメニューと競合、待ちが分かりにくい）、`confirm()`（文字が小さい）、1 段（誤タップ）
- 影響: DS §7-3、§12-14、`screen-spec.md` §4

### D11. トップに集計の数字を置かない。地図は入口にとどめる
- 根拠: spec §7「数字は控えめに」。frontend-design の禁止リスト「大きな数字＋小さなラベル」。委員の最初の画面は「送る」
- 採用しなかった案: 「未確定 3 枚」「判断済み 8 圃場」のタイル（管理者には便利だが、新着の「未確定 3枚」の文で足りる）
- 影響: `screen-spec.md` §1

### D12. 広い画面（960px〜）は 2〜3 列にするが、文章の列は 640px を超えない
- 根拠: 管理者が PC で確定する作業は、行が多く見える方が早い（Efferd の App Shell の考え方）。本文を広げると 1 行が 50 字を超えて読みにくい
- 採用しなかった案: 全部 640px の 1 列（PC で左右が空くだけ。確定フォームが行の下で縦に長い）、サイドバー（画面が 4 つしか無い）
- 影響: DS §5-2、§9、`screen-spec.md` の各「広い画面」

### D13. 今の画面の見た目の差分（DS §13）は L0 の締切の後、L1 の画面と一緒に当てる（11-04 本人決定。Q2）
- 根拠: L0 は 11/4 夜が締切で、実機（Android・iPhone・PC）で確かめた見た目を動かすと確認がやり直しになる。差分は小さい（S1〜S5、S7〜S9）が、麦色の意味（S2・S3）はコードの注釈も変わる
- 採用しなかった案: 今すぐ当てる（締切の前に確認の手間が増える）、当てない（Z1・Z4 が残る）
- 影響: 本人の `globals.css` の作業順。先輩には影響なし

### D14. アイコン・ロゴ・絵文字は画面に置かず、状態は文字の印で表す
- 根拠: 本人の「絵文字や装飾アイコンを避けたい」。印の文字（未確定・確定・収穫可能・収穫済）はそのまま読める。ロゴ・愛称は 11/6 に決まる予定で、それまで文字の「ear-to-ear」
- 採用しなかった案: 状態をアイコンで（屋外で小さな図形は判別しにくい。線幅をそろえる手間）、地図のピンを図形で（番号のラベルの方が速い）
- 影響: DS §6-4、§12-3、§12-12。例外は「←」（戻る道の先頭、既存）と根拠の写真の角の番号
