## 1. 要件の理解

### 1-1. 誰が・どんな場面で・何をするか

| 役 | 場面 | 端末 | すること | 出典 |

### 1-2. 最も重要な操作と情報

操作の重さの順（頻度 × 失敗したときの困り方）:

1. **送る**（委員。失敗すると共有されない。屋外で行う唯一の操作）
2. **見つける**（番号と日付で写真にたどり着く。サイトの中心、K14）
3. **確定・訂正**（管理者。間違いの責任の所在、K4）
4. **判断と理由を残す・たどる**（L1・L6。「根拠付きでたどれる」の中心、K14）

情報の優先順位（一覧でも詳細でも同じ）:

```
圃場番号（A-03） ＞ 状態（未確定／確定、収穫可能／収穫済） ＞ 撮影日 ＞ 写真 ＞ 理由・根拠・メモ ＞ そのほか（送った時刻、枚数、端末）
```

spec §7 の決まり: 「数字は控えめに。一覧では番号・日付・写真・判断の色だけ」「文字は大きめ、ボタンは押しやすく（屋外・手袋を想定）」。

### 1-5. 与えたい印象と、その理由

| 印象 | 理由 |

| **委員会の記録として信用できる** | 判断の責任の所在をはっきりさせる（K4）。言葉を盛らない、推定は推定と書く（AGENTS §4） |

### 2-3. 資料ごとの分析（8 つの軸で）

軸: レイアウト／タイポグラフィ／配色／余白／情報密度／画像／コンポーネント／操作時の表現。本文テキストから分からなかった軸は「不明」。

#### A. 部品集 11 件（KASUN の 5 件、best UI libraries の 6 件）

まとめて書く。個別の差より共通点が大きく、今回の扱いが同じだから。

| 軸 | 共通して見えたこと | 印象を生んでいる要素 |
|---|---|---|
| レイアウト | 「短いヒーロー 1 文 → 部品名の大量リスト → 利用者の投稿のループ → スポンサー → CTA」の LP 型。ベントグリッド | 大きな余白のヒーローと、数（50+・200+）の提示 |
| タイポグラフィ | 英語のみ。見出しは大きく、文字を 1 文字ずつ出す演出（Text Reveal・Typewriter・Split Flap） | 文字が「生成される」時間差 |
| 配色 | ダーク／ライト切替。ダーク地に発光（Aurora・Beams・Lamp・Neon）、グラデーション、ガラス（Liquid Glass・Rain Glass）（推定。部品名から） | 黒地と局所的な光のコントラスト |
| 余白・密度 | 密度は低い。1 画面 1 部品の見本 | 余白で「高そう」に見せる |
| 画像 | 写真はほぼ無い。WebGL・canvas の抽象（ディザ・粒子・液体金属）（推定） | 質感シェーダー |
| コンポーネント | 演出部品が 6〜9 割（ビーム・マーキー・3D カード・ドック・紙吹雪）。業務部品は Efferd（3:7）と Kokonut の入力部品だけ | ポインタと スクロールに反応する演出 |
| 操作時の表現 | ホバーで傾く・光る、磁力ドック、スクロール連動、スプリング | マウス前提 |

**取り入れる（原則として）**: 高コントラスト、状態の変化に小さな反応を付ける、`prefers-reduced-motion` を最初から考える（Ruixen が明記）、「送信中・読み込み中」の軽い表示（Efferd の Toast・Skeleton・Spinner の考え方。Dot Matrix の「小さく軽い」）、管理者の PC 画面を「画面単位で揃える」考え方（Efferd の App Shell・Dashboard）。

**合わない（理由つき）**:
- 発光・オーロラ・ビーム・ガラス・ぼかし: 直射日光下で見えない。写真の色を邪魔する。plain CSS で再現コストが高い。電池と CPU を使う
- ホバー・3D 傾き・磁力: スマホにホバーは無い。手袋では細かいポインタ操作ができない
- 文字の逐次出現・数字のカウントアップ: 圃場番号と日付を**即**読みたい場面で遅延になる
- ダーク地: 屋外ではライト地の方が読みやすい（推定。`color-scheme: light` の今の決定とも合う）
- LP 型の構成（ヒーロー・社会的証明・CTA）: この製品に説得の画面は無い。作業の画面は内容（写真と番号）で始める（oil-ui の 4）
- Kokonut の「長押しで確定」: 手袋の誤タップ対策として検討したが、長押しは iOS のコンテキストメニューと競合し、待ち時間が分かりにくい。代わりに「取り消し」を 2 段にする（`design-system.md` §7）

**実際の内容に合わせて変える点**: 部品の見た目は一切借りない。借りるのは「状態を見せる」「待ちを見せる」「画面の骨組み」の考え方だけで、値は `design-system.md` で自分で決める。

## 3. 方向性 3 案

3 案は配色の違いではなく、**情報の優先順位・文字の扱い・密度・レイアウト**が違う。

### 案 A「台帳」— 番号と日付を鍵にした記録簿

- **考え方**: 委員会の記録簿。1 行＝写真 1 枚か判断 1 件。番号（A-03）と撮影日が行の鍵で、写真はその行の添え物（小さな写真）。面は 1px の線で分け、色は状態の印だけに使う
- **適した場面**: 新着を流し読みして目的の畑・日付を見つける。管理者が未確定を上から順に確定する。判断の履歴と引き継ぎメモを読む
- **主な視覚的特徴**: 白地、1 列の行、左端に状態の印（未確定＝麦色の線、収穫可能＝緑、収穫済＝灰）、番号は太字で tabular の数字、写真は 120px（広い画面で 160px）。影なし。角は控えめ。動きは「送れた」の 1 か所だけ
- **長所**: 屋外で読める。番号と日付が最初に目に入る。実装が今の `globals.css` の延長で済む（期間内）。PC では行が増えるだけで崩れない
- **トレードオフ**: 写真の魅力は出ない。デモ動画で「映える」場面は少ない。写真を見比べる（L5）には向かない
- **参考資料との関係**: design-review・accessibility の数値をそのまま満たす。frontend-design の禁止リストに触れない。Efferd の「装飾を足さない」と同じ姿勢

### 案 B「アルバム」— 写真が主役の格子

- **考え方**: 写真を大きく並べ、番号と状態は写真の上の帯に重ねる。見つけるのは写真を眺めて
- **適した場面**: 撮影日ごとに写真を眺める（圃場ページ）。L5 の見比べ。動画で画面が映える
- **主な視覚的特徴**: 格子（スマホ 2 列、PC 4〜6 列）、写真の上に半透明の帯で番号・日付、背景は暗めの灰、文字は白
- **長所**: 写真の情報量を活かせる。1 画面に多くの写真
- **トレードオフ**: 写真の上の文字は太陽光下で読めない（写真の明るさで変わる）。「数字は控えめに」だが番号は**鍵**なので、写真の下に書くと行の高さが増えて密度が落ちる。未確定の写真は番号が無く、格子の中で浮く。判断・理由・引き継ぎメモ（文字の情報）を置く場所が弱い。暗い地はライト固定の今の決定と反する
- **参考資料との関係**: 部品集のギャラリー型に近い。oil-ui の「内容で始める」には合うが「焦点 1 つ」には合わない

### 案 C「地図の盤面」— 地図を玄関にした管理の画面

- **考え方**: `/` を地図＋集計（未確定 n 枚、判断済み n 圃場）の盤面にし、すべて地図から入る
- **適した場面**: 管理者が PC で全体を見渡す。動画の冒頭で「12 圃場が一目で」
- **主な視覚的特徴**: 広い画面で地図（左）＋一覧（右）の 2 ペイン、上に集計のタイル、ピンは判断の色
- **長所**: 全体の状態が一目で分かる。管理者には便利
- **トレードオフ**: 委員のスマホでは地図が画面を占め、「送る」「新着」までが遠い。地図は L1 で、タイル無しの架空の村を自分で描くので、地図が玄関だと L1 が遅れた時点で玄関が無い。集計のタイルは「大きな数字＋小さなラベル」の典型で、frontend-design の禁止リストに当たる。「数字は控えめに」と逆
- **参考資料との関係**: Efferd の Dashboard、部品集の「ダッシュボード」テンプレートに近い。テンプレート感が最も出やすい

## 4. 推薦: 案 A「台帳」を軸に、B の格子を圃場ページの中に、C の地図は入口にとどめる

**理由**:

1. 中心は「写真を見つける」「判断を根拠付きでたどれる」（K14）で、どちらも**番号・日付・状態・理由という文字の情報が鍵**。写真は証拠であって主役ではない。台帳の文法が合う
2. 唯一の屋外の操作（送る）と、流し読み（新着）は、白地・大きな文字・線で分けた行が最も読める。design-review・accessibility の数値をそのまま満たせる
3. 今の `globals.css` と部品の延長で作れる。L1（11/5）・L6（11/6）の新しい画面に力を使える。11/7 夕方以降に新しい段に手を付けない決まりに収まる
4. テンプレート感の源（ヒーロー、集計タイル、カード群、グラデーション、ガラス）を使う理由がこの製品に無い。台帳は「製品名を替えれば成立する汎用」ではなく、圃場番号・麦色の未確定・農協の判定という**この委員会の語彙**で組み立てる

**B から借りる所**: `/fields/[id]` の撮影日ごとの格子（今の `photo-grid`、スマホ 3 列）。写真の上に文字は重ねない（番号は見出しにあり、格子の中は写真だけ）。根拠の写真を選ぶ場面も同じ格子。

**C から借りる所**: `/` の地図は**圃場ページへの入口**で、集計のタイルは置かない。地図の下（広い画面では右）に 12 圃場の行（番号・名前・判断・未確定の有無）を置き、地図が描けなくても行だけで入口になる。

**この製品だけの要素**（汎用にならない根拠）:
- 麦色は「未確定」と ロゴにだけ。注意・警告には使わない（11-03 決定を文字どおりに守る）
- 「推定」「未確定」「日付不明」「根拠なし」は、文字に加えて**仮の見え方**（麦色の線・灰の文字・破線）を持つ
- 判断の色は 収穫可能＝緑、収穫済＝灰（11-04 本人決定。`design-decisions.md` D4）。「農協の判定で中止」は判断ではなく理由なので色を持たない
- 記憶に残る瞬間は「送れた」の 1 か所（送った後のまとめが画面の中に滑り込む）。ほかは静か
