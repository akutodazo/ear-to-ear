# 穴を突く実装（RED の穴を記録してから GREEN へ）

Issue: akutodazo/ear-to-ear#22。**状態: 提案（11-02）。T02 で一度試してから、採用するかを決める。** 採用するときは AGENTS.md §5 の「RED済み」の条件を変える（共有ファイルなので先輩の確認の後、別 PR）。

## 崩す前提
「人が書いて凍結したテストが通れば、実装は仕様を満たす」。テストに根拠が付いている（合格条件から書いた）ことと、テストが仕様の条項を網羅していることは別。無人運転の GREEN は、テストを通したまま条項を破れる（例: K6 の「距離を返さない」をテストが直接縛っていなければ、要素に距離を持たせても通る）。

## 手順（パケットごと）
1. **人が封をする**: 凍結テストと TASKS の合格条件を読み、「テストが見ていない条項」を先に書く（15分）。Claude の結果を見る前に書き、比較の基準にする
2. **別セッションの Claude Code（Opus）に破らせる**: 渡すのは凍結テスト、`src/types/`、`src/config.ts`、そのパケットの合格条件、関係する決定（K 番号）の文だけ。背景・経緯は渡さない
   - 指示: 「条項ごとに、テストをすべて通したまま、その条項を破る実装を書く。書けたら、実装と破り方を記録して次の条項へ。書けなければ、何に縛られたかを記録する」
   - 禁止: テスト・型・config の変更、コミット、push。条項ごとの試行は10分まで
   - 破り実装は**捨てる**。成果物は記録だけ
3. **記録**: `docs/run/HOLES-<パケット>.md` に、条項ごとに「破れた／縛られた」「破り方（要点）」「全件通過の vitest の出力」「対応」を書く
4. **人が決める**: 記録を読み、仕様違反でないもの（偽の穴）に印を付ける。残った穴に、テストを足す（RED。人が書く）か、受容と理由を書く
5. **GREEN へ**: テストを足した分の RED が済んでから、無人運転の GREEN に渡す。受容した穴は TASKS のパケット項目に残し、レビューの観点にする

## 範囲
| 誰が | 何を |
|---|---|
| Claude | どの条項を破れるか、破り方 |
| プログラム | 「全件通過」の事実（vitest の件数）。採用後は、運転開始の手順で HOLES の存在を確かめる |
| 人 | 穴が本当に仕様違反か。テストを足すか受容するか |

## 誤ったとき
- 偽の穴: 人の時間が減るだけ。印を付けて終わり
- 見逃し: 今と同じ
- 破り実装はコミットしないので、取り消しは不要。記録を直せば再開できる

## 既存の手法との関係
- TDD の「Evil Coder」制約（coderetreat）: 実装側がテストが通る限り好きなだけ変な実装をしてよい遊び。ここでは実装側を Claude にし、狙いを「仕様の条項」に限った
- Meta の ACH（Mutation-Guided LLM-based Test Generation、2025）: 関心事（例: プライバシー）に絞った疑似バグを作り、既存テストが捕まえないものだけ残して、テストを足す。発想は同じ。ACH は既存コードを変異させるが、ここでは実装が無い段階で凍結テストに対して書く
- コーディングエージェントの reward hacking の研究（ImpossibleBench・EvilGenie・SpecBench）: 「テストは通るが仕様を破る」を測る。この手順は、その行動をわざと起こさせてテストの監査に使う
- 条項の無い純粋な変換関数では、普通の仮の実装と変わらない。価値が出るのは条項が多い所（K6 の受信検査など）

## 最小実験（T02、半日）
- 成立条件: T02 の RED（13件）がブランチにあり、vitest が手元で回る
- 比べ方: 人が封をした一覧と HOLES
- 成功: 人の一覧に無い、仕様に関わる穴が1つ以上あり、各穴に全件通過の実行結果が付く。偽の穴が半分未満
- 失敗: 穴が全部「人も分かっていた」か偽、または通る実装が作れない。失敗なら、純粋関数には使わず、Worker 側（K6 の受信検査）のように条項の多い所だけに限る
- 人の時間: 実験全体で本人1時間。維持はパケットごとに15〜30分。無人 GREEN が1〜2時間遅れる
