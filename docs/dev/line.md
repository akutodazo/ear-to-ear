# L8 の LINE のお知らせ（人の手順と demo の台本）

状態: 11-05 先輩。コードは #143〜#147 と webhook（#140）・通知（#141）の PR。ここに書くのは **人がする作業**（LINE 側の設定・秘密の登録・グループ）と、2 人で見せる台本。決定は `docs/decisions.md` の 11-05。

## 仕組み（Workers だけ）
```
[LINE のグループ] ←── push（1 通）── [Worker] 判断を D1 に記録 → 応答 → waitUntil で送る
       │ 公式アカウントを招く                ↑ settings の line_group_id を読む・月の回数を数える
       └─ join ──→ [LINE] ──webhook──→ [Worker] POST /api/line/webhook（署名を確かめ、グループ ID を保存）
```
- 送るきっかけは、判断を残した（`POST /api/fields/:id/status`）・取り消した（`DELETE /api/status-events/:id`）ときだけ
- 本文は圃場番号・状態・理由の言葉・日本時間・判断のページの URL（`/api/judgments/<id>`、取り消しは `?revoked=1`）。**メモ・撮影位置は送らない**。根拠の写真の 1 枚目は、そのページの OGP で LINE のサムネイルになる（#220、11-07 先輩決定）
- 送れなくても判断の記録は成功する（合格条件 14）。月の送信は `LINE_STOP_AT`（180 回）の手前で止める
- 秘密が無い・`LINE_ENABLED` が `false` のときは、送らず、webhook は 503（本体は動く）

## 1. LINE 側の設定（人、15 分）
1. LINE の公式アカウントを作る（LINE Official Account Manager）。名前は架空のもの（例「ear-to-ear お知らせ（試作）」）。実在の委員会・人の名前を入れない
2. アカウントの設定で **Messaging API を有効にする**（LINE Developers のプロバイダーを選ぶ・作る）
3. 応答の設定: **応答メッセージ OFF・あいさつメッセージ OFF・Webhook ON**。アカウントの設定で **グループ・複数人トークへの参加を許可する** を ON
4. LINE Developers のチャネルで、**チャネルシークレット**（チャネル基本設定）と **チャネルアクセストークン（長期）**（Messaging API 設定）を確かめる。**会話・Issue・PR に貼らない**

## 2. 秘密の登録（人。Claude は手元からクラウドに触らない）
本体のフォルダで、値は聞かれたときに貼る:
```
npx wrangler secret put LINE_CHANNEL_SECRET --env dev
npx wrangler secret put LINE_CHANNEL_ACCESS_TOKEN --env dev
```
demo でも使うときは `--env demo` で同じく。止めたいときは `LINE_ENABLED` に `false` を入れる（秘密を消さなくてよい）。

## 3. Webhook の URL（人）
LINE Developers の Messaging API 設定で:
- Webhook URL: `https://<dev の URL>/api/line/webhook`
- 「検証」を押して **成功**（200）になること。503 なら秘密が入っていない、401 ならシークレットが違う
- 「Webhook の利用」を ON

## 4. 2 人のグループ（人）
1. 先輩と本人が、公式アカウントを友だちに追加する
2. LINE で 2 人だけのグループを作る（名前は架空。例「収穫委員会（試作）」）
3. グループに公式アカウントを招く → LINE から join が届き、Worker がグループ ID を `settings` に保存する
4. 確かめ: dev で判断を 1 つ残し、グループに届けば準備完了
5. **参加の許可は ON のままにする**。OFF にすると「参加しているグループから退出します」と出て、今のグループからも抜ける（11-05 に確認画面で確かめ、取り消した）。そのため、第三者が別のグループに招くと送り先が切り替わる弱点は残る（下の「弱点」）
   - 判断を残すには合言葉が要る。Chrome に入った状態が無いと「記録するには合言葉が要ります」と出る（11-05、入った後に押し直して届いた）

## 5. demo の台本（2 人、1 分）
1. 先輩のスマホで LINE のグループを開いておく（画面を映す）
2. 本人が dev の `/fields/A-03` で「収穫可能」を理由（穂の色・黄色い穂の割合）付きで残す
3. 数秒でグループに「A-03 収穫可能／理由: …／日時／URL」が届き、URL の下に根拠の写真のサムネイルが出る。タップすると判断のページが開き、そこから畑の詳細へ行ける
4. 本人が今の判断を取り消す →「A-03「収穫可能」の判断を取り消しました」が届く
5. 「メモに書いたことは LINE には出ない」ことを見せる（メモ付きで残しても本文に無い）

## 弱点（確かめていないこと）
- **数え方**: LINE はグループの人数ぶん数える（2 人のグループに 1 回送ると 2 通）。`LINE_STOP_AT` は送った回数で数えるので、2 人なら実際は 360 通ぶんまで送ろうとする。月 200 通の無料枠を超えると LINE が 429 を返す（記録は成功する）。直すなら共有の `src/config.ts` の値を変えるか、人数を掛ける（本人に確認）
- **無料枠の月の区切り**は日本時間の月と見ている（推定）
- **グループが 2 つ以上**: 最後に join したグループにだけ送る（`settings` は 1 行）。第三者が招いても切り替わる（レビュー #150・#151 の 1）。参加の許可を OFF にすると今のグループからも抜けるので、この方法では防げない。demo は 2 人だけなので、文書に残して直さない（11-05 先輩決定）。直すならコードで「一度覚えたら上書きしない」にし、送り先を変えるときは人が D1 の行を消す
- 公式アカウントの ID（`@` で始まる）を知っていれば誰でも友だちに追加できる。ID を公開の場所に書かない
- 委員の合言葉があれば、残す・取り消すの繰り返しで月の枠を使い切れる（費用は出ない）
- `wrangler dev` で試すと、本文の URL が localhost になる（要求の origin から作るため）
- 公式アカウントがグループから外されても `settings` は消えない（送ると LINE がエラーを返すだけ）

## 6. LINE に 1 枚（URL の共有でサムネイル、#159〜#163）
L8 の通知（Bot）とは別の道。トークンは使わない。
1. `/order` で確定した順の「1. 送る準備」→ 絵と番号の並びを `POST /api/shares` に送り、共有の URL（`/api/shares/<id>`）を受け取る（合言葉が要る）
2. 「2. LINE で送る」→ 端末の共有で文と URL を渡し、LINE を選ぶ
3. LINE のサーバーが URL を Cookie 無しで取りに来て、og:image（`/api/share-files/<id>`）をサムネイルにする

確かめ方（dev）:
- `curl -s https://<dev の URL>/api/shares/<id> | grep og:` で og:image が https の絶対 URL か
- LINE はプレビューを URL ごとに覚える。直した後は**新しい共有（新しい id）**で確かめる
- 60 日で 404。R2 の物は人が R2 のライフサイクル規則（接頭辞 `shares/`）を入れるまで残る

## 7. LINE から写真を受け取る（L9、#172）
設定は 1〜4 のままでよい（Webhook ON・グループに参加済み）。新しい秘密は要らない（同じチャネルアクセストークンで画像を取り、reply する）。
```
[委員] グループに写真を送る ─→ [LINE] ─webhook─→ [Worker] 署名 → 登録したグループの画像か → 200
                                              └ waitUntil: 1 日 30 枚を数える → LINE から画像を取る（3MB まで）
                                                 → 残すセグメントの種類を決める（DQT・DHT・SOF など。中身は写すだけ。APP・COM は読まずに捨てる）
                                                 → 長辺 1600px・JPEG の検査 → 二重を見る → R2・D1 に「未確定」 → reply で 1 回
```
- 受けるのは `settings` の `line_group_id` のグループだけ。1 対 1 のトーク・ほかのグループの画像は取りに行かない
- 新着には「未確定」（候補なし・撮影日なし）で入り、管理者が `/recent` で番号を付ける。送った人の LINE の個人 ID は残さない（端末は `line`）
- 1 回の webhook で 10 枚・20 秒まで、1 枚ずつ順に処理する。超えた分は「残りの N 枚は受け取っていません」と 1 通返す
- 1 日の上限（30 枚）に当たったら、その回の残りは取りに行かない（上限の返事は 1 通だけ）
- reply は月の上限（`LINE_STOP_AT`）に数えない

### 確かめる台本（2 人、実機）
1. 先輩がグループに、架空の写真（期間中に撮った・作ったもの）を 1 枚送る → 「写真を受け取りました（未確定）」と `/recent` の URL が返る。新着に出る
2. 同じ写真をもう一度送る → LINE が縮め直すので別の写真として入るか、「もう届いています」になるかを記録する（K7 の限界）
3. 3 枚まとめて送る → 返事は最後の 1 枚の分だけ
4. R2 の画像に撮影位置が無いこと: 新着の画像を保存して、Exif を読む道具で何も出ないことを見る
5. 縦に撮った写真が、新着で縦のまま出るか（Exif の向き・色のプロファイルも捨てるので、LINE が向きを画素に焼き込んでいなければ横倒しになる。PR #188 のレビュー 3）
6. LINE で届いた画像に Exif が残っていたかを記録する（残っていなければ privacy.md の「LINE の道では届きうる」を「LINE が消す」に書き直せる）

### 弱点（確かめていないこと）
- LINE で届く画像の大きさ（1600px を超えると断る）と、メタデータが残っているか（実機で未確認）。多くが断られるなら、LINE の分だけ上限を変えるか決める
- グループに送られた畑以外の写真も入る（管理者が見分ける。消す画面はまだ無い）
- waitUntil は応答の後 30 秒ほどで打ち切られる（推定）。20 秒の締め切りで次の写真を始めないようにしたが、締め切りの直前に始めた 1 枚が遅い（取得 10 秒＋返事 10 秒）と、その 1 枚は切られうる
- 残すセグメント（DQT など）は中身を確かめずに写す。表の後ろにわざと文字を足した画像なら残る（普通の端末は書かない。PR #188 のレビュー 4）
- 再送（同じ webhook がもう一度届く）でも 1 日の枚数を数える。写真はハッシュで二重を防ぐ
