# 依頼: LINE に送った写真をサイトの新着に入れる（#172、L9 の前倒し）

- 状態: **作るかどうかの相談**。11/7 の夕方以降は新しい段に手を付けない決まりなので、**11/7 の昼までに作るか見送るかを決めてほしい**
- Issue: #172

## 1. なぜ
委員はいまも LINE のグループで写真を送っている（本人の見立て。父にはまだ確かめていない）。グループに送った写真がそのままサイトの新着に「未確定」で入れば、委員はサイトを開かなくても共有できる。管理者（父）は `/recent` で番号を付ける。

## 2. 一番小さい形（案）
1. 委員が、登録したグループ（`settings` の `line_group_id`）に写真を送る
2. `POST /api/line/webhook` が `message` の `image` を受け取る（いまは `join` だけを処理している）。応答はすぐ返し、続きは `waitUntil` で行う（L8 と同じ形）
3. Worker が `GET https://api-data.line.me/v2/bot/message/{messageId}/content` で画像を取る（`Authorization: Bearer <チャネルのアクセストークン>`。トークンは L8 の `LINE_CHANNEL_ACCESS_TOKEN` を使える）
4. 今の送る流れと同じ検査をする: JPEG か、大きさ、APP1〜15、二重
5. R2 と D1 に入れる。番号は**未確定（候補なし）**、撮影日は**日付不明**か「LINE で送られた日」（§4-3）
6. グループに返事はしない（月の送信数を使わない）

画面の側（本人）は、新着に「LINE から」の印を付けるくらいで済む。

## 3. 調べて分かったこと（11-06）
### LINE の資料から（Messaging API のリファレンス）
- 画像のメッセージには `contentProvider.type` があり、`line` のときだけ上の API で中身を取れる。`external` のときは取れない（その画像は飛ばす）
- 中身は**送ってから一定の時間で自動で消え、どれだけ残るかの保証は無い**。webhook を受けたらすぐ取りに行く
- 中身は **LINE の側で縮小などの変換をされることがある**（大きさは決まっていない）。`/content/preview` は小さく変換した画像
- 何枚か同時に送ると `imageSet`（`id`・`index`・`total`）が付き、webhook は順不同で届く
- EXIF（撮影位置など）を消すかは、資料に書かれていない

### 手元で測ったこと（Node、本人の PC。Worker での実測ではない）
合成の JPEG で、今の検査（`inspectJpeg`）と SHA-256（`crypto.subtle.digest`）の時間を測った。

| 大きさ | inspectJpeg | SHA-256 |
|---|---|---|
| 0.5MB | 0.00ms | 0.6ms |
| 1.5MB | 0.01ms | 4.4〜5.7ms |
| 3MB | 0.02ms | 9.3ms |

区切りの検査はほぼ 0。ハッシュは 1MB あたり約 3ms。**今は二重を見分けるハッシュをブラウザが作っている**（`src/lib/sha256.ts`）ので、LINE の経路ではサーバーで作る必要がある。CPU 10ms の決まりの中に収まるかは、Worker で測るまで分からない（1.5MB までなら収まりそう、3MB はぎりぎり）。

## 4. 決めてほしいこと
1. **作るか見送るか**（11/7 の昼まで）。見送るなら Issue #172 に「提出の後」と書くだけ
2. **大きさの上限**: 今のサーバーは長い辺が `THUMBNAIL_LONG_EDGE_PX`（1600）を超える画像を `bad_dimensions` で断る（縮小はブラウザの仕事）。LINE の画像はそれより大きいことがある。Worker の中で縮小するのは CPU の決まりから難しい。案は次の 3 つ
   - 案 A（推奨）: LINE の経路だけ長い辺の上限を緩める（例 4096px、`MAX_UPLOAD_BYTES` の 3MB は保つ）。新着と見比べるは今の画像をそのまま出す。重いのは表示のときだけ
   - 案 B: 1600px を超えたら保存しない（グループに返事をしないので、送った人には分からない）
   - 案 C: `/content/preview` の小さい画像を保存する。見比べるには小さすぎるかもしれない
3. **撮影日**: EXIF が消えていれば撮影日は分からない。「日付不明」の枠に入れるか、webhook の `timestamp`（送られた時刻）を「送られた日」として使うか。使うなら、画面で撮影日と取り違えない書き方が要る
4. **APP1〜15 が残っていたとき**: 断るか、サーバーで取り除いてから保存するか。取り除く処理は区切りをたどってつなぎ直すだけなので軽い（`jpeg-segments` と同じ読み方）。撮影位置は読まない・保存しない（K6）
5. **二重**: SHA-256 で見るか（上の CPU の心配）、LINE のメッセージ ID で見るか（同じ写真を別のメッセージで送ると 2 枚になる）
6. **だれが送ったか**: LINE の個人 ID は残さない（`docs/privacy.md`）。新着には「LINE から」とだけ出す。送った端末の欄（`uploaderDevice`）に何を入れるか

## 5. 合格条件（案。テストに書いてほしいこと）
1. 登録したグループからの JPEG（`contentProvider.type: line`）は、新着に未確定で出る
2. 登録していないグループ・個人のトーク・`external` の画像は保存しない
3. 公開側の画像に APP1〜15 が無い。D1・R2 に撮影位置・LINE の個人 ID が無い
4. 同じ写真は 1 枚（§4-5 で決めた見分け方で）
5. LINE から取るのに失敗しても（時間切れ・404・消えた後）、webhook は 200 を返し、ほかの処理は止まらない
6. 署名の確かめ・64KB の上限は今のまま

## 6. 守ること
- 撮影位置は保存しない・読まない（K6）。公開側に APP1〜15 を残さない（AGENTS.md §1-4）
- デモの写真は実家のものを dev に入れている（11-04 夜の本人決定）。LINE を通すと LINE の会社のサーバーにも写真が残る。架空のグループの中だけで使う
- Claude API には送らない（K10）
