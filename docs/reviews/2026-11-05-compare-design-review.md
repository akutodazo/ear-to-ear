## 指摘（重い順）

### #1 選んだ畑を持って地図に戻ると、地図は最初の地区（北）に合わさり、選んだ畑が板の裏に隠れる — 直す
- **どこ**: `src/app/home-client.tsx` の `useState(() => ({ district: selected?.district ?? null, … }))`（`fit` の初期値）。`src/components/map/field-map.tsx` の `fitIfNeeded` → `keepSelectedVisible` の順
- **何が問題か**: 見比べるの A-09 から「地図」で戻ると、URL は `/#A-09`、地区の選択欄は「南地区」、板も A-09 なのに、地図は北地区の 4 区画に合わさっている。A-09 は左下に白い太線の端が見えるだけで、大半が板の裏にある。`/#A-11` を直接開いても同じだった（地区の欄は「南地区」、A-11 の中心は y=591 で、板の上端 y=565 より下）。`fit` の初期値は最初の描画のときの `selected` で決まるが、最初の描画ではハッシュがまだ読めていない（事前描画の値は null）ため、`fit.district` が null のまま最初の地区になる、と読める
- **なぜ**: 基準 §3「選択後もどの場所を見ているか分かる」、§5「選んだ畑と表示された写真の対応を見失わないか」。地区の欄と地図の中身が食い違い、戻った先で「どの畑を見ていたか」を探し直すことになる。見比べると地図を行き来する流れでは毎回起きる
- **直し方の案**: 最初の地区を `useState` の初期値ではなく、選択（ハッシュ）が読めた後に決める。たとえば「`fit.district` が null で `selected` があれば、その地区に合わせる」を描画のたびに判定する。合わせた後に `keepSelectedVisible` が効く順は今のままでよい

### #2 「昨年の同じ頃」の「昨年の判断の 6 日前の日付」が、収穫までの残り日数として読める — 直す
- **どこ**: `src/services/last-season.ts` の `lastSeasonLines` の 3 行目、`src/components/compare/last-season-note.tsx`
- **何が問題か**: A-04 では「2025年は小麦／7/25 に収穫可能と判断、7/29 に収穫済／今年の最新の写真（7/19）は、昨年の判断の 6 日前の日付」と出る。言葉は日付の差だけを言っているが、収穫の順番を考える画面で「判断の 6 日前」と書くと、ほとんどの人は「あと 6 日で刈れる」と読む。しかもこの畑は今年 7/22 に収穫可能と判断済みなのに、写真の日付と昨年を比べた行が残る
- **なぜ**: REVIEW-BRIEF §4「写真から収穫可否や日数を断定しない」、AGENTS.md「推定は推定と書く。水分・収穫の可否を Claude に言わせない」。引き算を画面が代わりにすると、予想を出したのと同じ効果になる
- **直し方の案**: 引き算の行を消し、日付を並べるだけにする。例「昨年 7/25 収穫可能 → 7/29 収穫済」「今年 7/22 収穫可能」のように、昨年と今年を同じ形で上下に並べる（差は見る人が読む）。今年の判断がまだ無いときは、昨年の日付だけを出す

### #3 写真を送っている途中で、いま見ている写真の日付と畑が画面から消える。目安の写真とも日付がずれる — 直す
- **どこ**: `src/components/compare/photo-stream.tsx`（日付は日ごとの見出しだけで、写真の上には何も無い）、`src/components/compare/benchmark-pane.tsx`（目安は最新の 1 枚に固定）
- **何が問題か**: 下へ送ると「2026年7月10日 2枚」の見出しが流れ去り、残るのは上の「目安 A-03 北の3 2026年7月19日」と、何も書いていない緑の写真だけになる。この写真が A-04 の何日のものかは、上の帯の丸い札（A-04）を見ないと分からない。目安は 7/19、下は 7/10 で、9 日違う写真を見比べていることに気付けない
- **なぜ**: 依頼の問い「目安と対象の対応を見失わないか」、REVIEW-BRIEF §3「選択後もどの場所を見ているか分かる」。見比べは同じ頃の写真どうしでないと意味が薄い
- **直し方の案**: 写真ごとに、目安の写真の帯と同じ形の小さな帯（「A-04 北の4 7/10」）を写真の下端に重ねる。目安の帯と左右の位置をそろえると、上下で対応が読める。可能なら、目安の写真も「いま見ている写真に一番近い日付」に切り替える（無理なら、日付が違うときだけ「目安は 7/19」と差を見せる）

### #4 判断の入力が長く、「根拠にする」と「記録する」の間を上下に往復する — 直す
- **どこ**: `src/components/compare/status-panel.tsx`、`photo-stream.tsx` の「根拠にする」、`.compare-body`（目安の写真が上に固定されるので、下の送れる範囲は 484px）
- **何が問題か**: 入力は高さ 524px あり、送れる範囲（484px）より大きい。開いた時点で「記録する」は画面の下にはみ出している（y=808）。根拠の写真を選ぶには、入力の下まで送って写真の「根拠にする」を押し（最初の写真で y=1193）、また上へ戻って「記録する」を押す。入力の中の「根拠の写真: 0 枚（下の写真の『根拠にする』で選ぶ）」は、この往復を文字で説明している。記録した後も入力は開いたままで、「記録しました」は送った位置によっては見えない
- **なぜ**: K1（委員の手間を増やさない）、REVIEW-BRIEF §3「文字のメニューだけに機能の意味を背負わせない」、§5「タップ範囲が無理なく使えるか」
- **直し方の案**: (a) 「記録する」を入力の中ではなく、入力を開いている間だけ画面の下（下の帯の上）に固定する。どこまで送っても押せる。(b) 根拠の写真の数を「記録する」の横に「根拠 1 枚」と出し、説明の文を消す。(c) 入力を開いている間は目安の写真を小さく（高さ半分）する。(d) 記録したら入力を閉じ、上の「7/22 に収穫可能と判断」の行を新しい判断に差し替えて一瞬強調する（いまも行は変わるので、閉じるだけでよい）

### #5 写真も目安も無い畑は、文字だけの画面になる。次にやること（写真を送る）が無い — 直す
- **どこ**: 南地区の A-09（目安なし・写真なし）。`benchmark-pane.tsx` の `kind: "none"`、`photo-stream.tsx` の空の表示
- **何が問題か**: 上から「この地区の目安の畑はまだ決まっていません」（黄色い地の帯）、「判断はまだありません」、「まだ確定した写真はありません」、「昨年の同じ頃 2025年は小麦…」、「まだ判断の記録はありません」と、文だけが縦に並ぶ。見るものが無く、この画面からできるのは「判断を残す」だけ。写真が無いなら一番自然な次の行動は写真を送ることだが、見比べるには「写真を送る」が無い（地図の上の帯にだけある）。目安なしの帯は注意の色（黄色）で、エラーのように見える
- **なぜ**: REVIEW-BRIEF §2「見るより読む感覚になっている」、§4「写真が少なくても成立する」、§3「機能のつながり」
- **直し方の案**: 写真が無いときの空の枠に「写真を送る」（カメラのアイコン付き、`/upload` へ。この畑の番号を渡せるなら渡す）を置く。目安なしの帯は普通の地の色で 1 行に。中身が無い段（判断の履歴が空など）は見出しごと畳み、空の段を並べない

### #6 「昨年の同じ頃」で一番強い文字が作物名（「2025年は小麦」）— 提案
- **どこ**: `last-season-note.tsx` の `.season-head`（18px 太字）、その下の日付は 17.1px の普通の太さ
- **何が問題か**: 小麦の畑では毎年「小麦」なので、見出しの強さに見合う情報になりにくい。大事なのは日付の方
- **なぜ**: REVIEW-BRIEF §2「情報の重要さと視覚的な強さを一致させる」
- **直し方の案**: 小麦の年は作物名を小さくし、日付を強くする（#2 の並べ方と合わせて）。小麦でない年だけ作物名を強く出す（輪作で比べられないことが要点なので）

### #7 「根拠にする ✓」の言い方と、選んだ写真の見た目 — 提案
- **どこ**: `photo-stream.tsx` の `.ref-toggle`
- **何が問題か**: 選んだ後も「根拠にする ✓」と動詞のままで、「これから根拠にする」のか「根拠にした」のかが紛らわしい。写真の方には印が付かず、送っていくと、どの写真を選んだかはボタンまで見ないと分からない
- **直し方の案**: 選んだら「根拠 ✓」にし、写真の枠を濃い緑の線で囲む

### #8 判断の履歴の「取り消す」が、1 回押すだけで確認なしに効く — 提案
- **どこ**: `src/components/compare/status-history.tsx` の `.history-revoke`
- **何が問題か**: 判断の行の右に枠付きのボタンで大きく出ていて、送っている途中の指で押しやすい。押すとすぐ取り消しになり、確認も元に戻す手段も無い（取り消しは履歴には残る）
- **直し方の案**: 押したら同じ場所が「本当に取り消す／やめる」に変わる二段にする。ボタンは文字だけ（枠なし）にして弱める

### #9 上の帯の畑の札が高さ 40px、写真を押すと素の画像が別のタブで開く — 提案
- **どこ**: `src/components/compare/field-switcher.tsx`（`.switcher-item` 高さ 40px）、`photo-stream.tsx`（`<a target="_blank">` で画像そのもの）
- **何が問題か**: 札は spec §7「ボタンは押しやすく（手袋を想定）」と、他のボタンの 44px よりわずかに小さい。写真を押すとアプリの外の素の画像に出て、戻り方が分かりにくい
- **直し方の案**: 札を 44px に。写真は同じ画面で全画面に広げる（閉じるで戻る）か、少なくとも同じタブで開く

## 良い点
- 目安の写真を上に固定し、この畑の写真を縦に送る形が、REVIEW-BRIEF §4 をそのまま形にしている。写真が画面の主役
- 目安の写真の帯に「目安」「番号・名前」「年つきの撮影日」がそろい、昨年の写真を今年に見せない
- 判断は「7/22 に収穫可能と判断」と、日付の意味を言葉で言っている（前回の #8 の対応が見比べるにも効いている）
- 判断の入力で必須は状態だけ。理由は押すだけの札で、農協の判定で中止の 2 つも入っている
- 上の帯の札で、地図に戻らずに同じ地区の次の畑へ移れる。目安の畑の札に金の印
- 目安の無い地区・目安そのもの・写真なしで、それぞれ別の言い方をしていて、空の枠で見栄えを作っていない
- 地図側: 選んだ畑の白い太線と濃い影は、塗りの色に頼らず浮いて見える。板の「判断はまだありません」と写真の枠のリンクも前回の指摘どおり

## 範囲外の気づき（参考）
- 判断の理由に「農協の判定で中止（水分超過）」「同（砕けなどの傷）」があるが、状態は「収穫可能／収穫済」の 2 つだけなので、「収穫可能 ＋ 農協の判定で中止」という組み合わせになる。中止のときにどちらの状態を選ぶのかを、本人と先輩で決めておくとよい（デザインより決定の話。spec §3 の L1）
