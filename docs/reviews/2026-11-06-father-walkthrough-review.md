## 指摘

### #1 委員長が写真を確定する「新着」と、管理者として入る所に、通常の画面から辿れない — 止める
- **どこ**: `/recent`。入口は `src/app/upload/upload-client.tsx` の「新着を見る」（送った直後のまとめの中）だけ。地図・見比べる・刈る順番・下の帯（`src/components/app-nav.tsx`）には無い。地図の板の「未確定の写真あり」（`src/components/map/selection-dock.tsx` の 82〜86 行）は、ただの文字
- **何が問題か**:
  - 送った写真はすべて「未確定」で入り、管理者が番号を確定するまで、見比べる・地図の板の写真に出ない
  - 委員が畑で送った写真を委員長が確定するには、委員長が自分で何か 1 枚送って「新着を見る」を押すか、URL を手で打つしかない
  - 「管理者として入る」も新着の画面にしか無い。刈る順番の「この順で確定」（管理者だけに出る）も、そこで一度入っていないと出ない
- **なぜ**:
  - AGENTS.md の「何を作るか」に「番号が決まらなくても『未確定』として先に共有し、管理者が確定・訂正する」とあり、中心は「写真を見つける」。spec の L0（必須）の「新着一覧・確定・訂正」に、画面から行けない
  - BRIEF §3「機能のつながり: 対象を見失わずに進める」
- **直し方の案**（小さい順。1 と 2 で通る）:
  1. 地図の板の「未確定の写真あり」を、`/recent`（その畑の未確定だけを開いた状態）へのリンクにする。押せる高さは 44px 以上にする
  2. 刈る順番の状態の行（「記録から並べた下書き」）の下に、管理者でない端末では「確定は委員長の端末で行います（委員長として入る）」を出す。押したら合言葉の欄を出す（`PassphraseForm` の使い回し）
  3. 地図の上の帯の「写真を送る」の横か、下の帯の上に「新着」への入口を置く（未確定の数の印つき）

### #2 刈る順番で「この順で確定」が出ない理由が画面に無い — 直す

- **何が問題か**: 委員の端末で確定が出ないのは仕様どおり。ただ、委員長の端末でも管理者として入っていないと、同じく何も出ない。父には「ボタンが無い」ことしか分からない
- **なぜ**: BRIEF §5「説明文を読まずに…分かるか」の逆で、読む文すら無い。委員長だけが行う操作なので、入り方は 1 行あってよい
- **直し方の案**: #1 の案 2 と同じ。委員の端末に出しても害は無い（確定はサーバーでも守る前提。いまは端末の中の保存なので、画面で出し分けるだけ）

### #4 「農協の判定で中止」が「収穫可能」か「収穫済」の理由としてしか残せない — 直す（決定に関わるので本人に確かめる）
- **どこ**: `src/components/compare/status-panel.tsx`（判断は「収穫可能」「収穫済」の 2 択で、理由は判断に付く）、`src/config.ts` の `STATUS_REASONS`
- **何が問題か**:
  - 父が農協に止められた日に記録しようとすると、どちらかの判断を選ぶ必要がある。結果は「収穫可能。理由: 農協の判定で中止（水分超過）」と残る
  - 地図ではその畑が黄緑（収穫可能）に塗られ、刈る順番では順位が付く
  - 引き継ぎメモも、その記録を「収穫可能と判断した」と引用する
- **なぜ**: K16 は「農協の判定は L1 の理由の選択肢として残す」と決めているが、理由を付ける先の判断が「可」か「済」しか無いので、止められた事実が逆の塗りで見える。AGENTS.md「言葉を盛らない」、BRIEF §4「写真から収穫可否…を断定しない」の趣旨に反して、記録の形が可否を言ってしまう
- **直し方の案**（推奨順。どれも決定 K16 の読み方に関わるので、本人の承認が要る）:
  1. 判断に「中止」（農協の判定）を足し、理由の 2 つはそこでだけ選べるようにする。地図では塗らず、印（斜線など）で示す
  2. 判断は 2 択のまま、農協の 2 つを選んだら記録の前に「この畑を収穫可能のままにしますか」と 1 段聞く。地図の塗りは「収穫可能（中止あり）」に変える
  3. 何も変えず、画面に「農協で止められたときは、収穫可能を取り消して理由を付けずに…」と書く（推奨しない。読ませる画面になる）

### #5 朝の「どこを見に行くか」が、刈る順番の一番下にあり、送る画面に畑が引き継がれない — 直す
- **どこ**: `src/components/order/next-to-shoot.tsx`（`/order` の一番下、上端 1006px）。その「写真を送る」は `href="/upload"` で、畑を渡さない（`src/hooks/use-upload.ts` は URL を読まない）
- **何が問題か**:
  - 場面 1 で一番要る「まだ判断の無い畑」が、「刈る順番」という名の画面の、並べ替えの一覧の下にある。地区ごとに 3 回切り替える
  - そこから「写真を送る」に行っても、どの畑のための写真か画面が覚えていない。位置の取れない写真では 12 択から選び直す
- **なぜ**: BRIEF §3「機能のつながり: 畑の選択 → 最新写真 → 比較・収穫順へ、対象を見失わずに進める」。spec §7「選んだ畑は 3 つの画面で同じ」が、送る画面だけ途切れる
- **直し方の案**:
  - 「次に撮る畑」の各行と、地図の板に「この畑の写真を送る」を置き、`/upload#A-01` で番号の選択を A-01 にしておく（委員が選んだ番号 `chosenFieldId` として送るだけなので、確定は管理者のまま）
  - 「次に撮る畑」を刈る順番の一覧より上に置く
  - または、地図の地区の選択の横に「まだ判断の無い畑 n」の入口を置く

### #6 送る画面・新着の画面に下の帯が無く、戻る言葉が「← トップへ」 — 見送ってよい

- **何が問題か**: ほかの 3 画面は下の帯と上の「地図」で戻るのに、この 2 つだけ「← トップへ」。送った後に「新着を見る」「続けて送る」はあるが、「この畑を見比べる」「地図に戻る」が無い

### #7 刈る順番の確定と LINE の送信が地区ごと（3 地区で 3 回） — 見送ってよい（本人に確かめる）
- **どこ**: `src/app/order/order-client.tsx`（地区の選択ごとに保存・確定・共有）
- **何が問題か**: 委員会が全地区の順をまとめて決めるなら、確定と送信を 3 回繰り返す（8〜10 回の操作が 3 回）。地区ごとに担当の委員がいて、地区ごとに送るのが自然なら、いまのままでよい
- **なぜ**: 手数（場面 4）。父の委員会の決め方に依存するので、推測で直さない
- **直し方の案**: 父に「刈る順番は地区ごとに決めるか、全体で 1 本か」を聞く。全体なら、確定した地区を 1 枚の文にまとめて送る「全地区をまとめて送る」を足す

## よい点
- **見比べるに入った瞬間に、目安の畑（上）と自分の畑（下）が同じ日で並ぶ**: 比べる相手を選ぶ手間が無く、場面 3 の中心が 2 回の押しで出る
- **取り消し・やめるが、どの書き込みにもある**:
  - 判断の取り消し
  - 確定の 2 段
  - 確定した順に戻す
  - 記録から並べ直すの 2 段
  - 送る前の「外す」

  父が押し間違えても戻れる。
- **LINE に送る文が短く、父の言葉に近い**（「この順にするよ」）。地図の絵は区画と順位の丸だけで、委員が地図を開かなくても順が分かる
- **昨年の引き継ぎ**: 4 回目の 5 件が直り、年が文ごとに付き、今年と取り違えない
- **本文の文字が 18px**: 補足（`.note`）も 17px で、屋外でも読める大きさ。15px 未満は、地区の帯の番号（15.3px）、昨年の印（14.4px）、「架空のもの」の注（11px）だけ

## 確かめられなかったこと
- 開発サーバーに Worker の API が無いので、判断・写真・送信・共有の URL は差し込みで作った
  - 本物の合言葉の流れ（401 → 合言葉の欄 → 送り直し）は通していない
  - 管理者として入っている状態がどれだけ続くか（セッションの長さ）も見ていない。続く長さによっては、#1・#2 の起きる頻度が変わる
- 位置と日付の付いた写真（候補「A-03（約120m）」が出る流れ）は、差し込みで作った合成写真にメタデータが無いので見ていない
- 「2. LINE で送る」の Web Share（端末の共有の画面）は、内蔵ブラウザに `navigator.share` が無いので見ていない。代わりの「2. 文と URL を LINE で送る」（44px、ブロックでない小さいボタン）が出るところまで見た
- 長押しでつかんで並べ替える操作は、▲ で代えた
- 内蔵ブラウザのパネルが隠れていたので、地図の絵は崩れて写った。大きさと位置は、画面の要素を測った値で書いた
