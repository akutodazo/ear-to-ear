## 指摘

### 1. 直す（PR の外）: Workers Builds が `harvest-share-dev` に繋がっていて、PR のブランチでも走る
- どこ: PR のファイルではない。#147 の先頭 `e54e439` の check-run「Workers Builds: harvest-share-dev」（app `cloudflare-workers-and-pages`、2026-11-05T08:01:20Z 開始、**failure**）。main の `015e994`・`b7e1727` にも同じ名前の check が **success** で付いている。それより前の main の commit には付いていない
- 理由:
  - `docs/dev/deploy-actions.md` と spec §10 では、dev へのデプロイは **GitHub Actions だけ**で、「PR（`pull_request`）では動かない」。Workers Builds は Cloudflare 側が自分の権限でビルド・デプロイする別の道で、手順書・decisions に書かれていない
  - PR のブランチでも走っている（#147 で失敗）。Workers Builds の既定では、本番のブランチ以外は「プレビューの版の upload」になり、**dev の秘密・D1・R2 のバインディングを持ったまま PR のコードが Cloudflare に上がる**ことがある（設定次第。ダッシュボードを見ていないので推定）
  - main では Actions と Workers Builds の 2 つが同時にデプロイしている可能性がある。デプロイのコマンドに `d1 migrations apply` が入っていれば migration も 2 本の道から流れる。#147 は `0003_settings.sql` を持つので、マージで両方が走る
  - この PR のコードが原因ではないので「止める」にはしない。ただし #147 をマージすると上のことが起きるので、マージの前に確かめるのが安全
- 再現の手順:
  1. `gh api repos/akutodazo/ear-to-ear/commits/e54e43922618d7cc6b847a3d08e16755149b5537/check-runs --jq '.check_runs[]|[.name,.conclusion,.app.slug]'` → `Workers Builds: harvest-share-dev failure cloudflare-workers-and-pages`
  2. 同じことを main の `b7e1727` で → `success`
  3. （人）Cloudflare のダッシュボードの `harvest-share-dev` → Settings → Build で、Git の連携・本番のブランチ・「本番以外のブランチのビルド」・デプロイのコマンドを見る
- 直し方の案: Actions に一本化すると決めているなら、Workers Builds の Git 連携を外す（推奨）。残すなら、本番以外のブランチのビルドを切り、手順書と decisions に 2 本目の道として書く。どちらも人がダッシュボードで行う

### 2. 見送ってよい: 正規でない base64 の見出しも通る（#144、弱点候補 1 と同じ）
- どこ: `src/services/line-signature.ts:14`（`BASE64_32`）・`:19`（`atob`）
- 理由: 32 バイトの base64 の 43 文字目は下位 2 ビットが使われない。正規表現は文字の種類だけを見るので、そこだけ違う見出しも同じ 32 バイトになって通る。ただし元の正しい署名を知っていないと作れないので、偽造にはならない
- 再現: 正しい署名の 43 文字目を、base64 の表で 1 つ隣の文字（インデックスの XOR 1）に変える → `verifyLineSignature` は true（Node で `atob` の結果が同じことを確かめた）
- 直すなら: 復号した 32 バイトを `btoa` で戻して見出しと同じか比べる。今は不要

### 3. 見送ってよい: 比べ方が JS のループ（#144）
- どこ: `src/services/line-signature.ts:30`（`equalsConstantTime`）
- 理由: 長さが同じなら最後まで XOR で比べるので、違う位置で早く抜けない。JIT の最適化で時間が完全に一定かは保証できないが、LINE の webhook は HMAC の出力を比べるだけで、推測に要る試行回数を考えると実害は無い。合言葉の照合（spec §6）は `crypto.subtle.timingSafeEqual` なので、揃えたいなら Service の比べ方を注入にする手もある
- 再現: なし（読んで確かめた）

### 4. 見送ってよい（webhook の PR で揃える）: 「webhook は 503」と spec §6 の「401」が違う（#147）
- どこ: `worker/deps.ts:75`（`line` のコメント「送らない・webhook は 503」）
- 理由: spec §6 の `POST /api/line/webhook` の失敗は 401 だけ。秘密が無いときに 503 を返すなら spec に足す（`handover` の `503 claude_disabled` と同じ形）、401 にするならコメントを直す。まだ webhook が無いので、この PR では決めなくてよい
- 再現: `docs/spec.md` §6 の表の `POST /api/line/webhook` の行と、`worker/deps.ts:75` を並べて読む

### 5. 見送ってよい: `LINE_STOP_AT` の数え方（#147、弱点候補 2 と同じ）
- どこ: `worker/deps.ts` の `LinePort.push`（1 回の push を 1 と数える前提）、`src/config.ts` の `LINE_MONTHLY_LIMIT = 200`・`LINE_STOP_AT = 180`
- 理由: LINE の無料枠の「通」は、グループへの push だと受け取る人数ぶん数える。架空のグループに 2 人なら 1 回で 2 通、90 回で枠を使い切る。無料のプランは枠を超えると送れなくなる（429）だけで、費用は増えない。spec §8 の 14「月の送信数が上限の手前で止まる」をどう数えるかは、usage-limit を使う PR で本人と決める
- 再現: なし（設計の確認）

### 6. 見送ってよい: 秘密が片方だけだと黙って止まる（#147、#144 の弱点候補 3 と近い）
- どこ: `worker/env.ts:78`
- 理由: トークンだけ・シークレットだけを登録すると `line` は null になり、何も出ない。安全側の動きなので直さなくてよい。秘密を登録する手順書に「2 つとも登録する」「登録後に webhook の検証ボタンで確かめる」を書いておくと、気づかない時間が減る
- 再現: `createDeps(fakeEnv({ LINE_CHANNEL_ACCESS_TOKEN: "x" })).line` → null（`worker/env-line.test.ts` の 1 件目）

### 7. 見送ってよい: すべての要求で `importKey` を呼ぶ（#147）
- どこ: `worker/env.ts:79`
- 理由: `createDeps` は要求ごとに呼ばれるので、LINE が有効なら写真の一覧などでも HMAC の鍵を 1 回作る。鍵の取り込みは軽く、CPU 10ms の決まりに響く量ではない。気になるなら `sign` の中で初めて作る形にする
- 再現: なし（読んで確かめた）
