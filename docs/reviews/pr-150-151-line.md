## 指摘

### 1. 直す（#151）: 誰でも公式アカウントを自分のグループに招けば、通知の送り先が切り替わる
- どこ: `worker/line-webhook.ts:36-37`（`joinedGroupIds(...).at(-1)` を `ON CONFLICT ... DO UPDATE` で上書き）。手順は `docs/dev/line.md` §1 の 3（グループへの参加を許可を ON）
- 理由:
  - 署名で守っているのは「LINE から届いた」ことだけで、「どのグループか」は守っていない。LINE の公式アカウントは ID や QR で誰でも友だちに追加でき、参加を許可していれば自分のグループに招ける。招いた時点で LINE が正しい署名つきの join を送るので、この Worker は**そのグループ ID で上書きする**
  - その後の判断の通知（圃場番号・状態・理由・日時・URL）は、知らない人のグループに届き、委員のグループには届かなくなる。データは架空で、同じ内容は公開の圃場ページでも見えるので秘密の漏れではない（だから「止める」にはしない）。ただし demo の途中に起きると「届かない」になり、月の枠もその人のグループで減る
  - `docs/dev/line.md` の弱点に「最後に join したグループにだけ送る」とあるが、第三者が起こせることまでは書かれていない
- 再現の手順（テストの形）:
  1. `worker/line-webhook.test.ts` の「2 回目の join は上書きする」がそのまま再現になる: GROUP_A の join の後に、別の人が招いた GROUP_B の join（正しい署名）を送ると、`settings.line_group_id` が GROUP_B になる
  2. 実機（人）: 委員のグループに招いた後、別の LINE アカウントで公式アカウントを友だちに追加し、別のグループに招く → dev で判断を 1 つ残すと、別のグループに届く
- 直し方の案（どれか 1 つ）:
  - **推奨**: 委員のグループに招いて ID が保存できたら、LINE Official Account Manager で「グループ・複数人トークへの参加を許可する」を OFF に戻す手順を `docs/dev/line.md` §4 に足す（コードを変えない。既に入っているグループから外れるかは未確認なので、人が実機で確かめる）
  - コードで守る: `line_group_id` が既にあれば上書きしない（`ON CONFLICT DO NOTHING`）。グループを変えたいときは人が D1 の行を消す（`--remote` は人の作業）
  - どちらにもしない場合は、`docs/dev/line.md` の弱点に「第三者が招くと送り先が変わる」と書く

### 2. 見送ってよい（#150）: 委員なら月の枠を短時間で使い切れる
- どこ: `worker/field-status.ts`（`deps.waitUntil(notifyLine(...))`）、`worker/status-events.ts`（同じ）。数えるのは `worker/line-notify.ts` の COUNT_SQL
- 理由: 判断を残す・取り消すは member 以上で、回数の上限は月の 180 回だけ。残す→取り消すを 90 回繰り返せば、その月の通知は止まる。上限の手前で止まるので費用は出ない（K15 のとおり）。委員は合言葉を知る身内なので、ハッカソンの範囲では見送ってよい
- 再現の手順: 委員の Cookie で `POST /api/fields/A-01/status` → 返った id に `DELETE /api/status-events/:id`、を 90 回繰り返す → `usage_counters` の `line:YYYY-MM` が 180 になり、以後は push が呼ばれない（#150 のテスト AT-2 と同じ止まり方）

### 3. 見送ってよい（#150）: 送った回数と LINE の数え方が違う
- どこ: `worker/line-notify.ts` の COUNT_SQL と `src/config.ts` の `LINE_STOP_AT = 180`
- 理由: LINE の無料枠は受け取った人数ぶん数える（`docs/dev/line.md` の記述による。このレビューでは LINE の文書を開いて確かめていない）。2 人のグループなら 100 回目あたりで LINE が 429 を返す。記録は成功し、#150 は結果を見ないので壊れない。`docs/dev/line.md` の弱点と、PR #144・#147 のレビューの #5 で既に挙がっている
- 再現の手順: 2 人のグループで判断を 101 回残す → LINE の push が 429 を返す（応答の 201 は変わらない）

### 4. 見送ってよい（#151）: join が A・B・A の順なら B を残す
- どこ: `worker/line-webhook.ts:36` の `.at(-1)` と、main の `src/services/line-webhook.ts` の `if (!ids.includes(groupId)) ids.push(groupId)`（先に出た順で重ねを除く）
- 理由: テスト名は「1 通に join が 2 つあれば最後のものを残す」。3 つで A が後ろにもう一度出ると、最後に出たのは A でも B が残る。LINE が 1 通に同じグループの join を 2 つ入れることは実際にはまず無いので見送ってよい
- 再現の手順: `eventsBody([joinEvent(GROUP_A), joinEvent(GROUP_B), joinEvent(GROUP_A)])` に正しい署名を付けて送る → `settings.line_group_id` は GROUP_B

### 5. 見送ってよい（#151）: 署名つきの古い本文の再送を拒まない
- どこ: `worker/line-webhook.ts`（`timestamp`・`webhookEventId` を見ない）
- 理由: 一度届いた join の本文と署名を持っていれば、後で送り直して送り先を前のグループに戻せる。ただし本文は LINE から Worker への HTTPS の中にしか無く、手に入れる道がほぼ無い。#1 の方がずっと簡単なので、こちらは見送ってよい
- 再現の手順: テストで、GROUP_A の join を送る → GROUP_B の join を送る → 1 回目と同じ本文・署名をもう一度送る → GROUP_A に戻る

### 6. 見送ってよい（#150）: URL の土台を要求から作る
- どこ: `worker/field-status.ts` の `ctx.url.origin`、`worker/status-events.ts` の同じところ
- 理由: Workers では要求の URL のホストは Cloudflare が振り分けた名前（`*.workers.dev` か設定したドメイン）なので、外から別の URL を混ぜることはできない。`wrangler dev` で LINE の口を有効にして試すと `http://localhost:8787/fields/A-03` が届くだけ。手元で秘密を入れて試すことは手順にないので見送ってよい
- 再現の手順: `.dev.vars` に LINE の秘密を入れて `wrangler dev`（人の作業）→ 判断を残す → 本文の URL が localhost になる
