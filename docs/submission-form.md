## プロジェクト概要：解決する課題と、誰のためのものか *（500 字まで）

（437 字）

北海道更別村では、小麦を地区ごとに共同で収穫し、刈る順番を委員会が毎年決めます。
委員はドローンで撮った畑の写真を LINE で送り合いますが、写真と畑の番号が別々に届くので、どの写真がどの畑か分かりません。
番号付けは一人の作業待ちになり、何を見て「刈れる」と決めたかも翌年の委員に残りません。

ear-to-ear は、収穫委員と委員長のための、写真と判断の共有サイトです。
スマホで写真を選ぶだけで、撮影位置から畑の番号の候補と撮影日が付き、すぐ全員に共有されます。
撮影位置はスマホの外に出しません。
地図の上で、同じ畑の前の日や昨年の写真と見比べ、「刈れるか」の判断を理由と根拠の写真付きで残せます。
判断から刈る順番の下書きを作り、確定した順番は LINE で共有できます。
1 年分の記録からは、Claude が引用機能で一文ごとに根拠を示した引き継ぎメモを書きます。

開発では、人がテストだけを書き、自作の MCP の道具だけを渡した無人の Claude が実装しました。

- 500 字に収めるため、前の版から削った内容: 「50 近く」の数（未確定だったため）、LINE のグループに送った写真の取り込み、取り消しても記録が残ること、ほかの共同作業への広がり、デモのデータが架空であること
- 【先輩】機能の書き方（LINE で共有・引き継ぎメモ）と、最後の「作り方」の一文が、作った中身と合っているか

## 開発中に一番詰まった場面 *（3,000 字まで）

（11-08 本人決定: 期間が始まる前に設計を固めた話に差し替え。
前の版は無人の Claude が止まった話、#112。
1,165 字）

### ① 何を作ろうとしていたか

開発期間は 6 日しかなく、いちばん足りないのは人が確かめる時間でした。
そこで、期間が始まる前に設計を固めておくことにしました。
作ろうとしていたのは 2 つです。
1 つは仕様書で、会話を知らない Claude でも同じ判断に行き着けるように、決まりと背景と理由をすべて書いたものです。
もう 1 つは、人がいない間に Claude が実装を進めるための決まり（無人運転の決まり）です。

### ② Claude にどう指示したか

Claude と対話しながら、仕様書と無人運転の決まりを書きました。
「撮影位置は端末の外に出さない」「実在の農家のデータを入れない」といった決定は、番号（K1〜K17）を付けて、理由と一緒に残すように頼みました。
書き上げたものは、別の会社のモデル（Codex）に点検させました。

### ③ 何が起きたか

点検の判定は、仕様書も無人運転の決まりも「通らない」でした。
仕様書では、致命的な指摘が 3 つありました。
いちばん重かったのは、候補の畑 3 つまでの距離をサーバーに送ると、圃場の位置と組み合わせて撮影位置を約 0.3 m の精度で逆算できる、というものです。
無人運転の決まりも 2 回続けて「通らない」でした。
指摘は、Claude が設定を書き換えればテストを通せてしまうことと、`npm run check; echo` のようにつなぐと、検査が失敗しても成功に見えることでした。

### ④ 期待していた結果と何が違ったか

「撮影位置を端末の外に出さない」と決めていたので、守れているつもりでした。
実際は、座標を送らなくても、距離から位置が分かってしまう設計になっていました。
無人運転の決まりも、Claude が守る前提で書いていて、守らなかったときに人が気づける仕組みになっていませんでした。
期間が始まる前の日まで、点検と書き直しが続きました。

### ⑤ どう対処したか

指摘はすべて受け入れました。
送るのは候補の畑の番号だけにし、距離はスマホの画面に出すだけにしました。
受け取る側でも、距離や座標の項目があれば受け付けません。
無人運転では、Claude に任せるのは実装だけにし、テストは人が書いて凍結しました。
変えてよいファイルを一覧にし、終わったら決まった検査を 1 つずつ実行させます。
手元で事前の試験もしました。
その中で、`git -C . push` という書き方が禁止の設定をすり抜けることが分かりました。
この抜け道は、push 先を無効にする設定と push の前の検査で止めました。
こうして固めた設計のおかげで、期間中は迷わずに進められました。
11 月 4 日には、人のいない Claude が 1 日でサーバーの機能 10 本を実装し、すべて検査に合格しました。

### ① 日本語や日本の業務で使う立場から気づいた欠点と利点

利点: 決まりの文書（AGENTS.md）に「やさしい日本語で、1 文を短く」と書くと、PR の本文・仕様書・委員向けの画面の言葉まで、その書き方でそろえてくれました。
農家の父に見せる画面の言葉（「収穫可能」「根拠なし」など）を、専門語を使わずに書けました。

欠点: 長い会話が要約されると、前に決めた細かい決まり（どこに push してよいか、など）を確かめ直す手間が出ました。
Windows の PowerShell と Git Bash の違いで、渡されたコマンドがそのまま動かないことがありました。

### ② 他の AI ツールと比べて劣る点と優れる点

点検に Codex（別の会社のモデル）を使うと、Claude 自身のレビューで見落とした指摘が出ることがありました。
書く側と点検する側を別のモデルにする価値がありました。
一方、Claude は決まりを守って止まり、推測で書かないので、無人の実装を任せやすかったです。
